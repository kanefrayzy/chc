# Техническое задание: онлайн-платформа CHCGREEN

> Рабочее название бренда — **CHCGREEN** (название должно быть параметризовано в конфиге, чтобы можно было заменить без правок кода). Платформа — продажа кодов для игры в стороннем казино + собственные мини-игры.

---

## 1. Краткое описание продукта

Веб-платформа, которая:
1. Позволяет пользователю зарегистрироваться, пополнить внутренний баланс (только AZN).
2. Предоставляет возможность **купить «код» для стороннего казино** через онлайн-чат с модератором.
3. Содержит **собственные игры** (Рулетка Battle — MVP; Джекпот и Кейсы — последующие фазы).
4. Имеет реферальную систему, ранги VIP, админ-панель.

Платформа работает локально на стадии разработки; домен и хостинг подбираются позже.

---

## 1.1 Принципы разработки

1. **Чистый, профессиональный код** по современным стандартам:
   - TypeScript strict mode на фронте и на бэке, без `any` без обоснования.
   - ESLint + Prettier с единым конфигом, обязательный pre-commit hook (Husky + lint-staged).
   - Conventional Commits, понятные сообщения коммитов.
   - Принципы SOLID, DRY, KISS; функции короткие, side-effects изолированы.
   - Все слои разделены: контроллеры/роуты → сервисы (бизнес-логика) → репозитории (БД). Без бизнес-логики в компонентах и роутах.
   - DTO и валидация входных данных (Zod) на каждом публичном эндпоинте.
   - Безопасность: OWASP Top 10, защита от SQLi (через ORM), XSS, CSRF, IDOR, race conditions на финансах (транзакции БД + блокировки).
   - Покрытие критичной бизнес-логики (платежи, ставки, выплаты) юнит-тестами; e2e на ключевые сценарии (регистрация, депозит, ставка, вывод).
   - JSDoc/TSDoc на публичных API; README в каждом значимом пакете.
   - Никаких «магических» констант — всё в конфигах/енвах.
   - Все суммы хранятся в **минорных единицах (qəpik = 1/100 AZN) как `bigint`/`Decimal`**, никаких `float` для денег.

2. **Правило принятия решений при сомнениях**
   - Если в процессе разработки возникает вопрос или развилка, по которой нет явного указания в ТЗ — **разработчик (Claude Opus 4.7) принимает решение самостоятельно, выбирая лучший индустриальный вариант**: безопаснее, проще в поддержке, ближе к стандартам отрасли (онлайн-гейминг / e-commerce / финтех), без ущерба производительности и UX.
   - Принятое решение **кратко документируется** в файле `docs/decisions.md` (формат ADR — Architecture Decision Record: контекст → решение → обоснование).
   - В сомнительных случаях по части UX/контента — выбирается вариант, соответствующий духу референса (тёмный, минималистичный, быстрый) и привычкам игроков CSGO/crypto-casino-платформ.

## 2. Технологический стек

| Слой        | Технология |
|-------------|------------|
| Frontend    | **Next.js 14+ (App Router)**, React, TypeScript, SSR/ISR |
| PWA         | Service Worker + manifest — **главное это быстрый сайт**; установка как приложение — приятный бонус, не основной сценарий |
| Backend     | **NestJS** (TypeScript) — отдельный API-сервис; либо API routes Next.js, если разработчик решит, что для текущего объёма этого достаточно (решение фиксируется в ADR) |
| ORM         | **Prisma** (миграции, типобезопасность) |
| БД          | **PostgreSQL 16+** |
| Real-time   | **Socket.IO** или нативный WebSocket — чат, рулетка, джекпот |
| Кэш/очереди | **Redis** (сессии, rate-limit, BullMQ для фоновых задач) |
| Хранилище   | S3-совместимое (MinIO для dev, S3/R2 для прод) |
| i18n        | **next-intl** — RU / AZ, JSON-локали |
| Стиль       | **Tailwind CSS** + shadcn/ui как база, кастомная тёмная неоновая тема через CSS-переменные |
| Аутентификация | JWT (access ~15 мин + refresh ~30 дней) в httpOnly + Secure + SameSite cookies |
| Валидация   | **Zod** (общие схемы для фронта и бэка через shared-пакет) |
| Тесты       | Vitest/Jest (unit) + Playwright (e2e) |
| Деплой      | Docker + docker-compose, CI/CD (GitHub Actions) |

Брендинг и название выносятся в `.env` / конфиг-файл (`SITE_NAME`, цвета через CSS-переменные).

## 5. Регистрация и авторизация

### 5.1 Поля регистрации
- Email (обязательно, валидация, уникальность)
- Телефон (обязательно, формат +994…, уникальность)
- Username / ник (обязательно, уникальный, 3–20 символов)
- Пароль (мин 8 символов, заглавная + цифра)
- Реферальный код (необязательно)
- Чекбокс «Мне 18+» и «Согласие с правилами»

### 5.2 Вход
- По email **или** username + пароль.
- «Запомнить меня» (refresh token на 30 дней).
- Восстановление пароля по email (письмо с одноразовой ссылкой).

### 5.3 Безопасность
- Хэширование пароля (bcrypt/argon2).
- Rate-limit на эндпоинт логина (5 попыток / 15 мин).
- CSRF-защита, httpOnly + Secure cookies.
- Возрастное ограничение 18+ (чекбокс при регистрации).
- **KYC не требуется**, верификация email/SMS — **не в MVP**.

## 7. Платежи

### 7.1 Пополнение

Интегрируются **два провайдера** (в последнюю очередь — после готовности остального функционала):

1. **Фиатный шлюз — Betra h2h** (карты AZN, P2P)
   - Документация: https://betra.game/betrah2h-docs.html
   - **Важно**: в UI пользователя, в админке и во всех видимых местах провайдер называется **«Limpay»** (бренд-обёртка). В коде, env и логах используется фактическое название (`betra_h2h`) для прозрачности интеграции.
   - Конфигурация: API-ключ, webhook secret — через env.

2. **Крипто-шлюз — WestWallet** (USDT TRC20/BEP20, BTC, ETH и т.д.)
   - Документация: https://docs.westwallet.io/en/
   - Поддержка webhook-уведомлений о статусе платежа.
   - Авто-конвертация в AZN по курсу на момент зачисления (курс — внутренний, синхронизируется с биржевым каждые N минут, источник настраивается).

Общие требования к платежам:
- Все операции в системе ведутся **в AZN** (минорные единицы — qəpik, целое число).
- Каждая транзакция — иммутабельная запись в `transactions` (idempotency_key, статус, провайдер, raw payload вебхука).
- Валидация HMAC/подписи вебхуков обоих провайдеров.
- Защита от replay-атак, идемпотентность.
- Минимальная/максимальная сумма депозита — настраивается в админке.
- Платёжная интеграция реализуется через **общий интерфейс** `PaymentProvider` — чтобы потом легко добавить ещё провайдеров без переписывания бизнес-логики.

### 7.2 Покупка кода для стороннего казино
Стороннее казино **не имеет API** — процесс полуавтоматический:

1. Пользователь нажимает **«Купить код»** в личном кабинете.
2. Открывается **онлайн-чат с модератором** (real-time).
3. Пользователь указывает сумму и подтверждает.
4. Система **резервирует сумму** на балансе пользователя (hold).
5. Модератор вручную создаёт код в стороннем казино и присылает его в чат.
6. Модератор нажимает кнопку «**Списать с баланса и закрыть тикет**» — деньги списываются, код доставлен.
7. Если что-то не так — модератор может отменить hold, средства возвращаются.

### 7.3 Вывод средств
Комбинированная система:
- Пользователь выбирает **способ**: автоматический (через настроенные платёжки в админке) **или** через модератора (чат).
- Автоматические выводы — мгновенные, в рамках суточных/разовых лимитов.
- Через модератора — заявка попадает в очередь в админке.
- Лимиты (мин / макс за раз / макс в сутки) — настраиваются в админке.

## 8. Чат с модератором

- **Real-time** на WebSocket.
- **История сообщений** сохраняется в БД, доступна обеим сторонам.
- **Отправка файлов/скринов** (чеки оплаты, скрин из казино) — в S3, с превью.
- **Шаблоны ответов** для модераторов (быстрые сообщения).
- **Несколько модераторов одновременно**:
  - Тикеты автоматически распределяются по принципу round-robin или «свободный модератор».
  - Модератор видит очередь тикетов, может «взять» свободный.
  - Передача тикета другому модератору.
- Индикаторы: «модератор печатает», «прочитано», статус тикета (open / waiting / closed).
- Внутри чата — **кнопки действий** для модератора:
  - «Списать с баланса N AZN»
  - «Вернуть hold»
  - «Подтвердить вывод»
  - «Закрыть тикет»

## 9. Игры

### 9.1 Рулетка Battle (MVP)

- **Многопользовательская**, как CSGO/Roobet-рулетка.
- Цвета: **Чёрный / Красный / Зелёный**.
- Коэффициенты по умолчанию (настраиваются в админке):
  - Чёрный — x2
  - Красный — x2
  - Зелёный — x14
- Раунд: ~15 секунд приём ставок + ~5 секунд анимация выпадения. Параметры настраиваются.
- Общий пул отображается всем игрокам в реальном времени.
- История последних N результатов на странице.
- **Provably Fair**: сервер заранее публикует хэш `SHA256(server_seed)`. После раунда раскрывает `server_seed`. Итог = HMAC(server_seed, public_seed) → номер слота. Public seed формируется из открытых данных (например, hash будущего блока публичного блокчейна или комбинация client-seed'ов).
- Минимальная и максимальная ставка — в админке.
- Защита от двойных ставок, проверка баланса на сервере.

### 9.2 Джекпот (Фаза 2)

- Каждые **N минут** (например, 1 минута) — раунд.
- Игроки кладут в общий банк любую сумму.
- **Шанс выигрыша индивидуальный**: `шанс_игрока = его_ставка / общий_банк × 100%`.
- В UI у каждого участника видно его текущий шанс и вклад.
- В конце раунда — анимация «крутящегося колеса» с именами участников (визуально как CSGO jackpot).
- Случайный победитель забирает банк **за вычетом комиссии платформы** (комиссия — настраивается, напр. 5–10%).
- **Provably Fair** аналогично рулетке.

### 9.3 Кейсы (Фаза 3)

- Каталог кейсов разного номинала (стоимость в AZN).
- В каждом кейсе — список призов с шансами (только денежные призы в AZN, в первой версии).
- Открытие кейса: списание с баланса → анимация прокрутки → начисление приза.
- Шансы и список призов настраиваются в админке для каждого кейса.
- **Provably Fair** аналогично.

## 10. Реферальная система

- Каждому пользователю — личная реф-ссылка и реф-код.
- **Одноуровневая** система.
- Начисления **на основной баланс реферера** (можно сразу играть/выводить):
  - **10%** от **проигрышей** рефералов.
  - **3%** от **выигрышей** рефералов.
- Статистика: количество приглашённых, активные, суммарные начисления, отдельная вкладка в профиле.

---

## 11. Ранги / VIP

- Расчёт по **суммарному объёму ставок** во всех играх.
- Например, 7–10 рангов (Bronze → Silver → Gold → Platinum → Diamond → VIP1 → VIP2 …).
- Каждый ранг — иконка/название и (опционально, в будущем) бонусы.
- Прогресс отображается в профиле.
- Пороги и названия рангов — настраиваются в админке.

## 12. Админ-панель

### 12.1 Роли

| Роль | Возможности |
|------|-------------|
| **Super Admin** | Полный доступ: финансы, пользователи, настройки, роли, игры, конфиги, шлюзы |
| **Moderator** | Чат, выдача кодов, обработка выводов, hold/возврат средств, бан/мут пользователя |

Все действия модераторов и админов логируются — **журнал действий** (кто, что, когда, IP).

### 12.2 Разделы

1. **Дашборд** — онлайн, депозиты/выводы за день, GGR, активные тикеты.
2. **Пользователи** — поиск, фильтры, карточка пользователя, ручная корректировка баланса (с обязательным комментарием), бан/разбан.
3. **Тикеты/чаты** — список, фильтры, передача между модераторами.
4. **Финансы** — депозиты, выводы (очередь, обработка), отчёты.
5. **Игры** — настройка коэффициентов, лимитов, шансов, комиссий, кейсов.
6. **Платёжные шлюзы** — вкл/выкл, реквизиты, лимиты.
7. **Реферальная система** — настройка процентов.
8. **Бонусы/ранги** — пороги, названия.
9. **Контент** — локализация, статичные страницы (Правила, FAQ, Политика).
10. **Журнал действий**.
11. **Настройки** — название бренда, цвета, контакты поддержки, лимиты.

**Принципы файловой организации**:
- Фронт — по фичам (feature-sliced логика), а не по типам.
- Бэк — по модулям бизнес-доменов.
- Вся логика «движка» (игры, fairness, payments) — в доменных модулях `api`, пользовательские интерфейсы — в `apps/web`.
- Общие типы/схемы (чтобы фронт и бэк не расходились) — в `packages/shared`.
- Добавление нового платёжного провайдера = добавить папку в `payments/providers/` и реализовать интерфейс.
- Добавление новой игры = новый модуль в `games/` + фича во фронте.

## 18. Этапы и приоритеты (MVP → Roadmap)

### MVP (релиз 1)
1. Регистрация / вход / профиль / восстановление пароля
2. Локализация RU/AZ, тёмная тема, PWA, адаптив
3. Пополнение баланса (агрегатор + крипта)
4. Реал-тайм чат с модератором + покупка кода (полуавтомат)
5. Вывод средств (авто + через модератора)
6. **Рулетка Battle** (Ч/К/З) + Provably Fair
7. Реферальная система (10% / 3%, 1 уровень)
8. Ранги VIP (по объёму ставок)
9. Админ-панель (Super Admin + Moderator, журнал)
10. Базовый антифрод, логи, лимиты

### Фаза 2
- **Джекпот** между игроками
- Бонусы (промокоды, +100% первого депозита, кэшбэк)
- Push-уведомления через PWA
- Расширенный антифрод

### Фаза 3
- **Кейсы**
- Native-приложения (если потребуется)
- Партнёрская программа (расширенная, многоуровневая)

## 19. Открытые вопросы (уточнить с клиентом)

1. **Лимиты по умолчанию**: мин/макс депозит, мин/макс вывод, дневные лимиты.
2. **Комиссия платформы** в Джекпоте — точный процент.
3. **Коэффициенты Рулетки Battle** — стандартные (x2/x2/x14) подходят?
4. **График работы модераторов** — 24/7 или есть «нерабочие часы» (нужен ли автоответ)?
5. **Тексты AZ** — сроки предоставления.
6. **Бренд-бук**: финальный логотип, финальная палитра, шрифт.
7. **Домен и хостинг** — подбор перед релизом.
8. **Юридическая модель** — оформляется ли юр-лицо, чьи реквизиты на счетах.
9. **Источник курса крипты** ≡ AZN (официальный ABS или биржа типа Binance + фиксированный спред).

> По всем вопросам, которые остались без явного ответа клиента на момент разработки, **разработчик принимает лучшее отраслевое решение** (см. §1.1) и фиксирует его в `docs/decisions.md` — это не блокер для продолжения работ.
