# ADR — Architecture Decision Records

Все нетривиальные решения, принятые в ходе разработки без явного указания клиента, фиксируются здесь. Формат: **Контекст → Решение → Обоснование → Последствия**.

## ADR-0001. Монорепо на pnpm + Turborepo

**Контекст**. Проект состоит из 4 приложений (web, admin, api, realtime) и нескольких общих пакетов (db, shared, ui). Между ними должны переиспользоваться типы, Zod-схемы, money-утилиты.

**Решение**. Использовать **pnpm workspaces** в связке с **Turborepo**.

**Обоснование**.
- pnpm — самый быстрый и экономный к диску менеджер, отлично работает с workspace.
- Turborepo даёт инкрементальную сборку и кэширование задач — критично для CI и DX в монорепо.
- Альтернатива (Nx) тяжелее, навязывает свой подход к генераторам; избыточно для текущего объёма.

**Последствия**. Все команды запускаются через `pnpm` / `turbo`. Docker-сборка использует pnpm в multi-stage образах.

## ADR-0002. Только prod-сборка Docker (без dev-overlay)

**Контекст**. Клиент явно попросил «сразу prod-версию без dev».

**Решение**. Dockerfile'ы — **multi-stage только prod**: `deps → build → runtime`. Никаких dev-зависимостей в runtime-образе, никаких `nodemon`/`tsc --watch`. Один `docker-compose.yml` для запуска всего стека.

**Обоснование**. Соответствует требованию клиента. Гарантирует, что в проде нет утечек dev-зависимостей и что то, что собирается локально, идентично тому, что пойдёт на сервер.

**Последствия**. Каждое изменение кода требует пересборки образа соответствующего сервиса. Если в будущем понадобится hot-reload — добавим `docker-compose.dev.yml` overlay, не трогая prod-конфиг.

## ADR-0003. Хранение денег как `BigInt` в минорных единицах (qəpik)

**Контекст**. Все операции в системе ведутся в AZN. Использование `float`/`number` для денег приводит к ошибкам округления и недопустимо в фин-системах.

**Решение**. Все суммы в БД — `BigInt` (Prisma `BigInt`, Postgres `BIGINT`), хранятся в **qəpik** (1 AZN = 100 qəpik). На границе с UI конвертация в строку `"123.45 AZN"` через утилиту в `packages/shared/src/money.ts`.

**Обоснование**.
- `BigInt` точен на любых разумных суммах, не имеет проблем округления.
- Соответствует индустриальным стандартам (Stripe, PayPal, банки).
- `Decimal` — альтернатива, но `BigInt` проще и быстрее, а нам не нужны дробные qəpik.

**Последствия**. Сериализация `BigInt` в JSON требует кастомного reviver/replacer (используем строки в API-ответах). Все суммы из платёжных провайдеров приводятся к qəpik при поступлении.

## ADR-0004. Брендинг Betra h2h ↔ Limpay _(упразднён — см. ADR-0007)_

**Контекст**. Клиент использует платёжный провайдер **Betra h2h** (https://betra.game/betrah2h-docs.html), но во всём пользовательском интерфейсе провайдер должен называться **«Limpay»**.

**Решение**. В коде, env, миграциях, логах — фактический ключ провайдера `betra_h2h`. В UI-локалях (`apps/web`, `apps/admin`) и пользовательских уведомлениях — отображаемое имя берётся из мапы `paymentProviderDisplayName` (`packages/shared/src/payment-providers.ts`), где `betra_h2h → "Limpay"`.

**Обоснование**. Разделение внутреннего идентификатора (стабильный, технический) и брендового имени (может меняться) — стандартная практика. Не теряется прозрачность интеграции для разработчика.

**Последствия**. Любой текст об этом провайдере, попадающий к пользователю, проходит через локализацию/мапу. Прямые upstream-логи и админка показывают `betra_h2h` (с подписью «Limpay» рядом).

## ADR-0005. NestJS как отдельный API-сервис (а не Next.js API routes)

**Контекст**. Backend-логика большая: модули auth, wallet, payments, chat, games, fairness, admin. Next.js API routes удобны для маленьких API, но плохо масштабируются на крупные доменные слои.

**Решение**. Отдельное приложение `apps/api` на **NestJS** (TypeScript). Next.js (`apps/web`, `apps/admin`) ходит в этот API через HTTP/REST.

**Обоснование**.
- DI и модульная архитектура NestJS подходят для крупного домена.
- Чёткое разделение: фронт деплоится отдельно от API, можно горизонтально масштабировать независимо.
- Realtime тоже отдельный сервис — единый паттерн.

**Последствия**. Чуть больше boilerplate, но окупается на длинной дистанции. CORS и auth решаются через httpOnly cookies + JWT.

## ADR-0006. Игра Mines: provably-fair RNG, активная игра как уникальный ресурс

**Контекст**. На платформу добавлена игра Mines (5×5, 1..24 мин). Игрок ставит, открывает клетки, забирает выигрыш в любой момент. Открытие мины = проигрыш ставки. Требуется честный RNG (provably fair), защита от одновременных активных игр и корректное распределение реферальных бонусов.

**Решение**.
1. **Provably-fair**: server seed (32 B) генерируется до старта, его SHA-256-хеш отдаётся клиенту вместе с client seed и nonce; раскладка мин = Fisher–Yates over `[0..24]` через HMAC-SHA256(serverSeed, "client:nonce:counter") c rejection-sampling. После завершения игры server seed раскрывается — игрок сам пересчитывает.
2. **Множители**: формула `(1 − houseEdge/10000) × Π_{i=0..picks-1} (25-i)/(25-mineCount-i)` (в bps, дом-эдж 1% по умолчанию). picks=0 даёт ровно ×1.0000 (плюс отдельный гард `NO_REVEALED_TILES` против cashout без открытий).
3. **«Одна активная игра на пользователя»** — реализовано **частичным уникальным индексом** в БД (`CREATE UNIQUE INDEX ... WHERE status='ACTIVE'`) поверх `MinesGame(userId)`. Сервис ловит `P2002` и возвращает `GAME_ALREADY_ACTIVE` — race-safe под высокой нагрузкой.
4. **Реалтайм**: эмит идёт в существующую комнату `user:{id}` через `RealtimeGateway.emitToUser` событием `mines:state`. Новых широковещательных каналов нет — игра single-player.
5. **Реферальные бонусы**: считаются по чистой марже казино за игру (`bet − payout`). Если казино в плюсе → `FROM_LOSS` (10%); если в минусе (редкий low-mines cashout) → `FROM_WIN` (3%). Это честнее, чем начислять всегда от полной ставки.
6. **Денежная точность**: `BigInt` qəpik. Выплата вычисляется как floor(bet × multBps / 10000) — никогда не переплачиваем.

**Обоснование**. Provably-fair — индустриальный стандарт прозрачности. Партиальный уникальный индекс — единственный надёжный способ гарантировать «одна активная игра» без распределённого лока. HMAC-SHA256 + rejection sampling даёт криптографически качественную равномерность. Дом-эдж не на старте, а только после первого открытия — иначе игрок мог бы поставить 0-pick cashout и стабильно терять ~1%.

**Последствия**. Любой клиент может проверить раскладку постфактум. Конкурентные `POST /mines/start` от одного пользователя безопасны. WebSocket-инфраструктура не разрастается. Реферальная модель Mines идентичная Roulette по экономике (нет двойного списания).

## ADR-0007. Замена платёжного провайдера Betra h2h на Betatransfer

**Контекст**. Клиент попросил полностью снести интеграцию Betra h2h и подключить **Betatransfer** (https://docs.betatransfer.io/).

**Решение**.
1. Новый провайдер `apps/api/src/modules/payments/betatransfer.provider.ts`, ключ enum `BETATRANSFER` (вывод — `AUTO_BETATRANSFER`). Значения enum в Postgres переименованы миграцией `ALTER TYPE ... RENAME VALUE` — существующие депозиты/выводы сохранены.
2. Флоу депозита — **редирект**: `POST /api/payment?token=<API_KEY>` (form-urlencoded) возвращает `url` платёжной страницы, он сохраняется в `Deposit.paymentUrl` (UI уже умел показывать кнопку «Оплатить»). Реквизиты карты (`externalAddress`) больше не используются.
3. Подпись запроса: `md5(конкатенация значений параметров в порядке отправки + secret)`. Подпись вебхука: `md5(amount + orderId + secret)`. Вебхук приходит form-urlencoded на `/webhooks/deposits/betatransfer` (env `BETATRANSFER_CALLBACK_URL` передаётся как `urlResult`).
4. `fullCallback=1`: приходят и промежуточные статусы (`pending`, `checkPayment`, ...). В `ParsedWebhook.status` добавлено значение `PENDING` — контроллер отвечает 200 и не трогает депозит. Маппинг финальных: `success`/`partial_payment` → COMPLETED (для partial зачисляется `paidAmount`), `not_paid_timeout` → EXPIRED, `cancel`/`not_paid`/`error`/`blocked` → FAILED.
5. Конфиг платёжного метода: `{ paymentSystem?: string }` (код платёжной системы выдаёт менеджер Betatransfer; без него система выбирается на платёжной странице).
6. Брендинг «Limpay» (ADR-0004) был обёрткой именно для Betra и удалён вместе с ним: в UI провайдер отображается как «Betatransfer» (пользователь видит в основном названия методов из админки, а не провайдера).

**Обоснование**. Redirect-флоу — единственный базовый сценарий Betatransfer (H2H требует PCI-полей карты плательщика). Переименование значений enum вместо новых значений — минимальная миграция без backfill.

**Последствия**. env-ключи `BETRA_H2H_*` удалены, добавлены `BETATRANSFER_API_URL/API_KEY/API_SECRET/CALLBACK_URL`. Вебхук-URL нужно указать менеджеру Betatransfer / в кабинете и в env. Выводы остаются ручными (модератор), автопейаут `/api/withdrawal-payment` не подключён.

**Дополнение (V2 P2R, реквизиты на сайте)**. Клиент прислал «API Documentation V2»: для P2P-систем существует `POST https://api.betatransfer.io/v2/p2r/create` (JSON; заголовки `ApiKey`/`Timestamp`/`Signature = HMAC-SHA256(timestamp + body, secret)`), который возвращает реквизиты (`requisite.data.card`, банк, владелец) сразу в ответе — редирект не нужен. Провайдер выбирает флоу по `config.paymentSystem`: `P2R*` → V2 с реквизитами (`Deposit.externalAddress`, `externalId` = id заказа Betatransfer, срок из `expired_at`), иначе → V1 redirect. Колбэк V2-заказа не содержит md5-подписи V1, поэтому используется как триггер: статус верифицируется подписанным `GET /v2/p2r/{id}` (статусы `processing|paid|partial_paid|expired|failed`; при `paid/partial_paid` зачисляется `customer_amount`). `verifyAndParseWebhook` стал асинхронным.

## ADR-0008. Антиминус реферальной программы: бонус с накопленной маржи казино

**Контекст**. Аудит экономики показал, что реферальные выплаты уводили казино в минус. `FROM_LOSS` (10%) начислялся с **полной ставки** проигравшего в Mines и Classic, тогда как дом-эдж этих игр 1% и 7%. Пример: Mines 24 мины, ставка 1000 qəpik — казино зарабатывает 10 qəpik ожидаемо, а платит рефереру 100 qəpik с каждого проигрыша. Три схемы сговора давали группе аккаунтов +4.5%…+11.5% от оборота. Дополнительно `FROM_WIN` (3%) платился, когда казино в убытке, что делало выгодным «отмывание» ставок между двумя аккаунтами. В рулетке база считалась корректно (GGR), но ставки только на GREEN всё равно давали −2.67% дому: проигрыш случается в 14 случаях из 15, и 10% с него превышают эдж 6.67%.

**Решение**. Единая точка начисления — `ReferralsService.settleGameMargin({ referredId, marginMinor })`, где `marginMinor = ставка − выплата` (отрицательна, если игрок выиграл).

1. У пользователя появилось поле `User.referralCarryMinor` — накопленная маржа казино по этому игроку, ещё не отработанная бонусом.
2. На каждом расчёте: `carry += margin`. Если `carry <= 0` — выплаты нет, долг переносится вперёд. Если `carry > 0` — платим `rateBps` от `carry` и обнуляем его (оставшиеся 90% — доход казино, вперёд не переносятся).
3. `FROM_WIN` в играх больше не начисляется: это была выплата в момент, когда казино теряет деньги. Настройка `referral.from_win_bps` осталась в БД для совместимости, но не используется.
4. Все три игры переведены на новую модель: Mines (проигрыш → маржа = ставка, кэшаут → `bet − payout`), Classic (проигравшие → их вклад, победитель → `stake − payout`), Roulette (агрегированный GGR игрока за раунд, включая отрицательный).

**Обоснование**. Выплата привязана к тому, что казино реально заработало на конкретном игроке, поэтому реферальная программа не может стать источником убытка ни при какой стратегии, включая сговор нескольких аккаунтов и концентрацию ставок на GREEN. Проверено тестами `referral-margin.spec.ts`.

**Последствия**. Реферальный доход стал меньше и «отложенным»: после крупного выигрыша реферала выплаты приостанавливаются, пока минус не отыграется. Остаётся разовый стартовый перерасход (бонусы, выплаченные до первого крупного выигрыша игрока) — он ограничен и отыгрывается на дистанции; удержание маржи сходится к 90%. Если нужен нулевой риск и на старте — начислять бонус периодами (например, раз в неделю по итогам NGR), а не по каждой игре.

## ADR-0009. Атомарные списания баланса и условные переходы статусов

**Контекст**. Аудит безопасности нашёл гонки во всех денежных путях. Списание везде было «прочитать баланс → сравнить → записать decrement». При уровне изоляции READ COMMITTED (по умолчанию в Prisma) параллельные запросы читают один и тот же баланс, все проходят проверку и все списывают — двойная трата и уход баланса в минус. Аналогично: пользовательская отмена вывода и одобрение модератором читали статус без блокировки, и заявка могла быть одновременно возвращена на баланс и выплачена.

**Решение**.
1. Хелпер `common/balance.ts → debitBalance(tx, userId, amount)`: условие «хватает средств» перенесено в сам `UPDATE ... WHERE balanceMinor >= amount`; Postgres перепроверяет `WHERE` после снятия блокировки строки, поэтому второй запрос получает `count = 0` и транзакция откатывается. Используется в roulette, mines, classic, withdrawals, code-purchases и админской корректировке.
2. CHECK-констрейнт `"balanceMinor" >= 0` в БД как последний рубеж.
3. Переходы статусов заявок на вывод — через `updateMany({ where: { id, status: ... } })` с проверкой `count === 1` (и у пользователя, и у модератора).
4. Classic: строка раунда блокируется `SELECT ... FOR UPDATE` перед выдачей диапазона билетов, банк растёт через `{ increment }` — иначе диапазоны пересекались, а часть денег не попадала в банк. Ставки после истечения отсчёта отклоняются (`BETTING_CLOSED`) — раньше они списывались, но не могли выиграть.

**Обоснование**. Условный `UPDATE` — стандартный способ решить lost update без перехода на SERIALIZABLE (который дал бы откаты под нагрузкой игрового цикла). Идемпотентные ключи транзакций остаются вторым рубежом.

**Последствия**. Все денежные операции безопасны при параллельных запросах из нескольких вкладок/скриптов. Ошибка `INSUFFICIENT_FUNDS` теперь может прийти и в момент, когда клиент считал баланс достаточным — это корректное поведение при гонке.

## ADR-0010. Проверка вебхуков платёжных провайдеров запросом к API

**Контекст**. Вебхук WestWallet не проверялся вообще (в коде стоял комментарий про IP-фильтрацию на nginx, но такого правила в конфиге не было). Любой мог отправить `POST /webhooks/deposits/westwallet` с `label` своего депозита и произвольной суммой и получить баланс. У Betatransfer V1 подпись `md5(amount + orderId + secret)` вырождалась в вычислимую кем угодно, если `BETATRANSFER_API_SECRET` не задан, а `status` и `paidAmount` вообще не входят в подписываемый набор.

**Решение**. Телу вебхука не доверяем — оно только триггер.
1. WestWallet: по `id` транзакции из IPN делается подписанный `POST /wallet/transaction`; статус и сумма берутся из ответа API, `label` сверяется. Без настроенных ключей вебхук отклоняется (fail closed).
2. Betatransfer V2 (P2R): статус подтверждается подписанным `GET /v2/p2r/{id}`.
3. Betatransfer V1: при пустом секрете вебхук отклоняется.
4. Сырые тела вебхуков и заголовки больше не пишутся в лог целиком (там валидные подписи).

**Обоснование**. Подпись по данным, которые сам же злоумышленник и присылает, защищает только при корректно настроенном секрете; обращение к API провайдера даёт независимый источник истины и не зависит от настроек окружения.

**Последствия**. Обработка вебхука делает исходящий HTTP-запрос (метод `verifyAndParseWebhook` стал асинхронным). При недоступности API провайдера вебхук вернёт ошибку и будет повторён провайдером — это безопаснее, чем зачислить неподтверждённый платёж.

## ADR-0011. Эквайринг с авто-редиректом и выплаты через API Betatransfer

**Контекст**. У мерчанта два метода ввода (P2P `P2R_AZN` и эквайринг `Card_AZN`) и один метод вывода (`USD_CardAZN`). P2P выдаёт реквизиты для перевода прямо в ответе API, эквайринг же требует ввода карты на стороне провайдера — реквизитов там не существует. Выплаты до сих пор делались модератором вручную.

**Решение**.
1. **Выбор флоу по методу**: `config.paymentSystem`, начинающийся с `P2R`, идёт через V2 P2R (реквизиты на сайте, `paymentUrl` не сохраняется). Остальные системы — V1 `POST /api/payment`, где возвращается `url` платёжной страницы; фронт делает **автоматический редирект** сразу после создания счёта (`window.location.href`), без промежуточной кнопки. Если игрок вернулся на сайт с неоплаченным счётом эквайринга, в карточке показывается кнопка «Продолжить оплату» — иначе счёт блокировал бы новые пополнения до истечения таймера.
2. **Режим выплат** — настройка `withdrawal.auto_mode` (админка):
   - `manual` — как раньше: модератор платит сам и фиксирует факт в админке;
   - `semi` — модератор нажимает «Одобрить», а выплату отправляет система (`POST /api/withdrawal-payment`); заявка переходит в `PROCESSING` и закрывается колбэком;
   - `auto` — выплата уходит провайдеру сразу при создании заявки, без участия модератора.
   В режимах `semi`/`auto` суммы выше `withdrawal.manual_threshold_minor` всё равно уходят модератору. Код платёжной системы задаётся настройкой `withdrawal.payout_payment_system` (по умолчанию `USD_CardAZN`).
3. **Сумма выплаты** передаётся как `paymentAmount` + `paymentCurrency=AZN` — это то, что получит игрок на карту. Списание с баланса мерчанта в USD провайдер считает сам по своему курсу, поэтому игрок всегда получает ровно запрошенную сумму, а курсовая разница и комиссия остаются на стороне казино.
4. **Колбэк выплаты** — `POST /webhooks/withdrawals/betatransfer`, подпись `md5(amount + orderId + secret)`. `success` → заявка `COMPLETED` и hold списывается окончательно; `cancel`/`error` → заявка `FAILED` и деньги возвращаются игроку (идемпотентно, по ключу `withdrawal:{id}:refund`).

**Обоснование**. Ошибка провайдера при автовыплате не отменяет заявку — она просто остаётся модератору, поэтому включение автомата не может «потерять» вывод. Порог ручной обработки сохраняет контроль над крупными суммами.

**Последствия**. Нужны env `BETATRANSFER_PAYOUT_CALLBACK_URL` и код платёжной системы выплат от менеджера. Баланс мерчанта в Betatransfer должен быть в USD и достаточным — при нехватке средств API вернёт ошибку, и заявка уйдёт модератору.

## ADR-0012. Лимиты выплат: отдельный метод вывода и расшифровка отказов провайдера

**Контекст**. После того как менеджер Betatransfer открыл доступ к API выплат (до этого приходил `403 You have no permissions`), выплаты продолжали падать — уже с `422 Minimum amount: 30 USD`. Замеры через валидацию API (заведомо неверный номер карты, поэтому заявка не создаётся) дали границы `USD_CardAZN`: минимум **30 USD ≈ 51 AZN**, максимум **1750 USD ≈ 2975 AZN**. Метод «Карта AZ» был `kind=BOTH` с минимумом 10 AZN — подходящим для пополнения и заведомо ниже границы выплаты. Модератор при этом видел безликое `PAYOUT_PROVIDER_ERROR`.

**Решение**.
1. **Разделили метод на два**: «Карта AZ» остаётся `DEPOSIT` (P2R, минимум 10 AZN), для вывода заведён отдельный `WITHDRAWAL`-метод с лимитами 55–2900 AZN и `config.payoutPaymentSystem = "USD_CardAZN"`. `sendPayout` берёт код платёжной системы сперва из конфига метода, затем из `withdrawal.payout_payment_system`, затем дефолт.
2. **Отказы провайдера переводятся в текст** (`BetatransferPayoutError.reason`): лимиты, нехватка баланса мерчанта, невалидная карта, IP вне белого списка, отсутствие доступа к API. Модератор получает причину вместо кода ошибки.

**Обоснование**. Лимиты провайдера заданы в USD, наши суммы — в AZN, поэтому запас в 4 AZN над границей 51 AZN покрывает колебания курса конвертации. Отдельный метод вывода — единственный способ развести лимиты ввода и вывода: в `PaymentMethod` одна пара `min/max` на обе стороны.

**Последствия**. Лимиты правятся в админке без деплоя. Минимальный вывод для игрока вырос с 50 до 55 AZN. API выплат ограничен по IP на стороне провайдера — проверять его можно только с прод-сервера.

## ADR-0013. Прогрессивный джекпот: отчисления из маржи, срыв вручную

**Контекст**. Нужен блок GRAND/MAJOR/MINOR/MINI на главной. Клиент выбрал вариант «копится реально, разыгрывает админ»: суммы должны быть настоящими, но момент выплаты остаётся под контролем казино.

**Решение**.
1. Четыре строки `ProgressiveJackpot` (по одной на уровень). С каждой ставки в рулетке, Mines, классическом и лотерее в каждую включённую копилку уходит `contributionBps` от суммы ставки, округление вниз.
2. **Отчисление берётся из маржи казино, а не из выплаты игроку.** Математика игр (RTP, множители) не меняется — меняется только доход дома. Иначе пришлось бы пересчитывать house edge каждой игры при каждой правке процента.
3. Пополнение вызывается после коммита транзакции ставки и не может её уронить: ошибка только логируется. Копилка — витрина, ставка важнее.
4. Срыв делает модератор из админки: вся сумма уходит на баланс выбранного игрока, копилка откатывается к `seedMinor`. Сброс — условный `updateMany` по текущему значению, поэтому два одновременных нажатия не выплатят джекпот дважды.

**Обоснование**. Автоматический случайный срыв при малом обороте либо не срабатывал бы месяцами, либо требовал сложной настройки вероятностей. Ручной розыгрыш даёт тот же эффект для игроков и полный контроль над расходом.

**Последствия**. Суммы растут медленно и отражают реальный оборот — витринных миллионов не будет. Стартовые суммы и проценты правятся в админке. Выплата логируется в аудит (`progressive.award`).

## ADR-0014. Боты в ленте последних выигрышей

**Контекст**. Лента на главной пустеет, когда на сайте мало игроков, — это выглядит хуже, чем отсутствие ленты. Клиент попросил добавить ботов «для более красивого эффекта».

**Решение**. `BotWinnersService` держит записи в памяти и добавляет новую раз в 20–75 секунд, храня последние 40 за 40 минут. Записи подмешиваются в ленту и сортируются вместе с реальными по времени. Суммы распределены реалистично: 55% выигрышей ×2–×5, крупные ×50+ — реже 3%. Отключается настройкой `winners.bots_enabled`.

**Обоснование**. Держать ботов в памяти, а не в БД — потому что это витрина: они не участвуют в расчётах, не влияют на баланс, ранги, реферальные начисления и джекпот. Появление по расписанию (а не случайная генерация на каждый запрос) не даёт ленте «прыгать» между обновлениями страницы.

**Последствия**. Лента никогда не пуста. Строгое ограничение: боты существуют только в ответе `/roulette/recent-winners`; любые денежные показатели считаются исключительно по реальным записям.

## ADR-0015. Магазин кодов: товар + пул кодов вместо выдачи через чат

**Контекст**. Коды стороннего казино выдавал модератор вручную в тикете. Это медленно и не работает ночью.

**Решение**. `CodeProduct` (номинал + **отдельная цена** + остаток) и `CodeItem` (готовый код из пула). Покупка списывает цену с баланса и занимает код условным апдейтом `status: AVAILABLE` в WHERE — два покупателя не могут получить один код; при гонке транзакция откатывается и повторяется до трёх раз. Старый чат-флоу остаётся: вывод средств по-прежнему оформляется через поддержку.

**Обоснование**. Цена отдельно от номинала позволяет делать скидки и наценки, не перезаливая коды. Удаление номинала запрещено, если по нему были продажи — иначе теряется история покупок игрока.

**Последствия**. Коды нужно заливать заранее; при пустом складе игрок видит «нет в наличии». Остаток и продажи видны в админке.

## ADR-0016. Лотерея «три в ряд»: таблица призов и RTP

**Контекст**. Нужна моментальная лотерея по образцу Scratch! Gold, но со ставкой 0.5 AZN вместо 3$.

**Решение**.
1. Призы заданы **множителями к ставке** (bps), а не абсолютными суммами: цена билета меняется настройкой `lottery.bet_minor`, RTP при этом не плывёт.
2. Шансы заданы весами из пула в 10 000 000 билетов. RTP получается ровно **96%** и проверяется тестом на целых числах.
3. Номиналы округлены до сумм, которые ровно ложатся в qəpik. Прямое масштабирование таблицы оригинала (÷6) давало призы вроде 8.33 и 0.1667 AZN — их нельзя выплатить без потери копеек.
4. Максимум сохранён как в оригинале: ×100 000, то есть 50 000 AZN при билете 0.5 AZN, шанс 1 к 10 000 000.
5. Карта строится так, что случайной второй тройки быть не может: выигрышный символ встречается ровно три раза, остальные — не больше двух. Provably fair по той же схеме, что Mines.

**Обоснование**. RTP, зашитый в веса, считается точно и не зависит от эмпирики: тест на выборке шумит на единицы процентов (один приз ×1000 при 60 тыс. билетов — это +1.7% отдачи), поэтому проверяется совпадение частот с весами, а сам RTP — аналитически.

**Последствия**. Дисперсия высокая: приз 1000 AZN выпадает примерно раз на 100 000 билетов, 50 000 AZN — практически недостижим, но возможен. Игру можно выключить настройкой `gameplay.lottery_enabled`, выигрыши от 1000 AZN пишутся в лог отдельной строкой.

## ADR-0017. Переводы: встроенный файл — база, ответ API — накладка

**Контекст**. Сайт брал словарь локали целиком из `GET /translations/:locale` и подставлял его вместо встроенного файла. API отдаёт копию `apps/web/src/i18n/messages`, вшитую в **свой** образ при сборке. Стоило выкатить веб с новыми ключами, не пересобрав api, — сайт получал старый словарь, и вместо текста показывались сами ключи (`lottery.buy`, `codeShop.title`). Так и произошло: шесть новых разделов пропали на всех страницах.

**Решение**. `loadMessages` в `apps/web/src/i18n/request.ts` всегда читает встроенный файл как базу и накладывает ответ API поверх него рекурсивным слиянием. Ключ, которого нет в ответе API, берётся из файла. Тот же порядок уже действует внутри `TranslationsController` для DB-оверрайда.

Админка правит переводы **по одному ключу**: `GET /admin/translations/:locale` отдаёт плоский список `{ key, defaultValue, value, overridden }`, `PATCH` принимает только изменённые ключи, а значение, совпавшее с дефолтом, из оверрайда удаляется (`null` сбрасывает ключ явно). Старый режим «сохранить весь JSON» из интерфейса убран: он записывал в БД полный снимок словаря, после чего любые правки текстов в коде навсегда перекрывались этим снимком.

**Обоснование**. Правки из админки должны побеждать — но только там, где они есть. Замена целиком превращает любой рассинхрон образов в поломку интерфейса, причём тихую: страница отдаёт HTTP 200 и «переводится» без единого русского слова, так что проверка на остатки чужого языка её пропускает.

**Последствия**. Устаревший api больше не ломает витрину — в худшем случае свежие ключи показываются на языке файла, а не из админки. Строки плиток «Poz Qazan» и «Kod al» переехали из кода в `landing.games.*`, поэтому их теперь можно править из админки, как остальные.

Снимок, накопленный старым редактором, на проде вычищен: из 312 переопределённых ключей в каждом языке 303 дословно повторяли встроенный текст и были удалены, 9 настоящих правок (тексты hero, `auth.login.title`) сохранены. Значения на сайте при этом не изменились — сверено до и после.

## ADR-0018. Лимит частоты не должен считать серверный рендер за одного клиента

**Контекст**. На тестовом запуске (~50 человек одновременно) сайт отдавал 500 на страницах: за три часа 4 322 ответа 500 при пике 2 314 запросов в минуту. Сервер при этом простаивал — 4 ядра, load average 0.2, ни одного перезапуска контейнеров. В логах web 9 116 исключений `ApiException: ThrottlerException: Too Many Requests`.

Причина: глобальный лимит `300 запросов / 60 секунд` считается по IP. Страницы рендерятся на сервере, и web ходит в API из контейнера — то есть **все посетители приходят с одного адреса**. Счётчик общий на весь сайт. Умножало проблему то, что один рендер главной делал около двенадцати запросов к API: `/settings/public` дёргался семь раз (макет, шапка, меню, hero, плитки, страница), `/auth/me` — трижды, `/translations/:locale` — на каждый заход целиком. Порог выбирался примерно за 25 просмотров страниц в минуту, дальше API отвечал 429, SSR падал с исключением, и Next отдавал 500.

**Решение**.
1. `InternalAwareThrottlerGuard`: запросы с заголовком `x-internal-client`, совпадающим с `INTERNAL_API_KEY`, из-под лимита выводятся. Заголовок ставят только серверные вызовы web/admin, в браузерный бандл он не попадает, снаружи API недоступен. Трафик из браузера по-прежнему ограничен по IP пользователя.
2. Повторные запросы схлопнуты: публичные настройки кэшируются в процессе на 15 секунд, словарь переводов — на 60 (столько же живёт кэш настроек в самом API), `getServerUser` обёрнут в `cache()` React и делается один раз за рендер.
3. Отказ API больше не убивает страницу: баланс на страницах игр и `/auth/me` при 429/503 деградируют до гостевого вида вместо 500.
4. Лимиты входа и регистрации подняты (5/час → 25/час на регистрацию, 10/5 мин → 30/5 мин на вход): мобильные операторы держат абонентов за общим NAT, из-за чего 47 живых регистраций получили отказ.

**Обоснование**. Лимит частоты защищает от внешних злоупотреблений, а собственный SSR — не внешний клиент. Считать его по IP контейнера бессмысленно: порог упирается в число посетителей, а не в нагрузку. Кэширование бьёт по той же причине с другой стороны — оно снижает число запросов на порядок и остаётся полезным независимо от лимитов.

**Последствия**. `INTERNAL_API_KEY` обязателен в окружении: без него web попадает под общий лимит и всё повторится. Правки настроек и переводов доезжают до витрины с задержкой до 15 и 60 секунд соответственно.
